# Design: Grocery tab — shopping list, trip log, and monthly spend metrics

Generated by /office-hours on 2026-09-01
Branch: main
Repo: habittracker (Routiner)
Status: APPROVED
Mode: Builder

## Problem Statement

Grocery shopping happens on a loop and leaves no trace. Before a shop there is a
list in your head; during the shop there are prices you forget by the time you
get home; at the end of the month there is no answer to "how much did I spend,
where, and was it more than last month". Routiner already owns the daily-habit
loop on this phone, so the grocery loop belongs in the same app rather than a
second one.

Verbatim ask: a Grocery tab holding a things-to-buy list, an entry flow for what
was actually bought (milk 1 litre skimmed €1.15, onion 1 kg €0.99), the store it
came from picked from a separately maintained list (Lidl, Esselunga, Conad), the
purchase date, an optional expiry date, and metrics such as "September: 6 shops,
4 Lidl, 2 Esselunga, €200 total, less than August".

## What Makes This Cool

The list you write before leaving is the same object you tick in the aisle, and
ticking it with a price is what produces the ledger. One pass of typing produces
both the shopping list and the spend history — no receipt re-entry at the
kitchen table, which is the step that kills every grocery app.

## Constraints

- Personal, single-user, offline. No accounts, no sync, no server.
- Everything lives in the existing zustand store persisted to AsyncStorage and
  must ride the existing backup export/import contract (`DATA_KEYS`).
- No new dependencies. The app already has every primitive this needs.
- Single currency: euro, decimal.
- The tab bar is a floating pill with an `ICONS` map keyed by route name; a
  fourth tab has to look native to it.

## Premises

Confirmed with the user (D2, all seven accepted):

1. The **trip is the unit of record**, not the loose item. "6 shops, 4 Lidl"
   is trip-shaped; loose item rows carrying a store and a date make trip count
   a guess when two runs land on the same day.
2. The to-buy list is the **on-ramp to a trip**, not a separate island. Ticking
   a list line with a price converts it into a purchased line on the open trip.
3. A trip can be logged **without itemizing** — "€43.20 at Lidl on Saturday" is
   a complete record; itemize only when the detail matters.
4. Stores are a **small registry with their own lifecycle** (add / rename /
   archive), seeded with Lidl, Esselunga, Conad.
5. Euro only, no conversion.
6. Expiry is a **field plus an "expiring soon" shelf, not a notification**.
   Alerts stay a later add-on; the notification service already exists.
7. Everything stays **local** in the persisted store (persist v5 + migration)
   and lands in the existing backup export.

## Approaches Considered

### Approach A: One screen, three sections
`GroceryScreen` with a `SegmentControl` (List · Trips · Insights), modals for
entry, store registry as a sheet. Ships fastest, smallest diff. Rejected: typing
prices into a modal while standing in an aisle is cramped, and the insights
section has nowhere to grow.

### Approach B: Hub plus pushed screens (chosen)
Tab is a hub (active list, this-month summary, expiring-soon strip); the busy
work lives on its own pushed screens — live shop, trip detail, insights, stores.

### Approach C: Shopping-mode first
The tab opens as a live session; ledger and metrics sit behind it. Rejected: it
buries the month view, which is half of what was asked for.

## Recommended Approach

**Approach B.** It matches the pattern the app already uses (Home hub pushing
HabitDetail / Calendar / Settings), gives the in-shop flow a full screen with a
sticky running total, and leaves the insights screen room for the per-store
split and month-over-month comparison.

### Data model — `src/data/grocery.ts`

```ts
export type Unit = 'pc' | 'kg' | 'g' | 'l' | 'ml' | 'pack';

export type Store = { id: string; name: string; archived?: boolean };

/** A line on the to-buy list. Ticking it in a shop turns it into a TripItem. */
export type ListItem = {
  id: string;
  name: string;            // "Milk"
  note?: string;           // "skimmed"
  qty?: number;
  unit?: Unit;
  done: boolean;
  addedOn: string;         // YYYY-MM-DD
};

export type TripItem = {
  id: string;
  name: string;
  note?: string;
  qty: number;
  unit: Unit;
  price: number;           // euros paid for this line
  expiresOn?: string;      // YYYY-MM-DD
};

export type Trip = {
  id: string;
  storeId: string;
  date: string;            // YYYY-MM-DD — the shopping date
  items: TripItem[];
  /** Set when the shop is logged as a lump sum; null means "sum the items". */
  manualTotal: number | null;
  status: 'open' | 'closed';
  createdAt: string;       // ISO
};
```

Store slice: `grocery: { stores: Store[]; list: ListItem[]; trips: Trip[] }`.

Actions on `useStore`: `addStore` / `renameStore` / `archiveStore`;
`addListItem` / `updateListItem` / `removeListItem` / `toggleListItem` /
`clearBoughtFromList`; `startTrip(storeId, date)` / `addTripItem` /
`updateTripItem` / `removeTripItem` / `setTripTotal` / `closeTrip` /
`deleteTrip`; and the converter `buyListItem(tripId, listItemId, {qty, unit,
price, expiresOn})`, which appends a `TripItem` and marks the list line done in
one `set()`.

### Metrics — pure selectors in `src/services/grocery.ts`

Pure functions over `trips`, so they are unit-testable without rendering:

- `tripTotal(trip)` → `manualTotal ?? sum(items.price)`
- `monthKey(dateKey)` → `YYYY-MM`
- `monthSpend(trips, monthKey)` and `monthTripCount(trips, monthKey)`
- `storeBreakdown(trips, stores, monthKey)` → per store: trips, spend, share
- `monthOverMonth(trips, monthKey)` → `{ current, previous, deltaAbs, deltaPct }`
- `expiringSoon(trips, today, days = 5)` → items with `expiresOn` inside the
  window, soonest first, each carrying its trip's store
- `avgPerTrip(trips, monthKey)`
- `topItems(trips, monthKey, n)` → most-bought names by spend

September reads out as: `monthTripCount = 6`, `storeBreakdown = [Lidl 4 trips
€x, Esselunga 2 trips €y]`, `monthSpend = 200`, `monthOverMonth.deltaAbs < 0`.

### Screens

1. **`GroceryScreen`** (the tab). Month summary card (spend, trips, delta vs
   last month), shopping list with an inline add field, "Expiring soon" strip
   when non-empty, a primary "Start a shop" CTA, the last three trips, and
   links into Insights and Stores.
2. **`ShopTripScreen`** (pushed). Store chips + date at the top, the to-buy list
   below — tapping a line opens a compact price/qty/expiry row — plus a free
   "add something not on the list" field, a sticky footer running total, and
   "Finish shopping" to close the trip. A "just log a total" control writes
   `manualTotal` for the no-itemizing case.
3. **`TripDetailScreen`** (pushed). Read and edit a past trip: items, total,
   store, date, delete.
4. **`GroceryInsightsScreen`** (pushed). Month scrubber in the style of
   `ActivityScreen`'s offset control, total spend, trip count, per-store split
   bars (trips and spend), month-over-month delta, average per trip, top items.
5. **`StoresScreen`** (pushed). Add, rename, archive. Archived stores stay
   attached to historical trips but drop out of the picker.

### Wiring

- `MainTabs` gains a fourth `Tabs.Screen name="Grocery"`; `TabBar`'s `ICONS`
  map gains `Grocery: BasketIcon`, a new `makeIcon` entry in
  `src/components/icons.tsx` with its path in `src/assets/icons/svgs.ts`.
- The four pushed screens register on the root stack next to `Calendar` and
  `HabitDetail`.
- `DATA_KEYS` gains `'grocery'`; persist `version` goes 4 → 5 and
  `migrateStore` seeds `{ stores: SEED_STORES, list: [], trips: [] }` for
  existing installs.

### Reuses

`Card`, `PrimaryButton`, `SecondaryButton`, `SegmentControl`, `SectionHeader`,
`IconButton` from `src/components/common.tsx`; `AppText` variants; the theme
tokens (with the `ink60`-for-small-text rule from the last design review);
`ActivityScreen`'s month-window and bar patterns for Insights; `toDateKey` /
`todayKey` from the store.

## Open Questions

Deliberately out of v1, worth a later look:

- Per-item price history ("milk was €1.15 last time, €1.25 now").
- Categories or aisles for the list.
- Recurring staples that repopulate the list each week.
- A receipt photo attached to a trip.
- Expiry notifications (premise 6 keeps them out for now).
- Budget target per month with a progress ring.

## Success Criteria

- A shop can be logged end to end in under a minute: open tab, start a shop,
  tick three items with prices, finish.
- The September example reproduces by hand: 6 trips, 4 Lidl / 2 Esselunga,
  €200, shown as down versus August.
- A trip logged as a lump sum with no items still counts in every metric.
- Backup export and re-import round-trips the grocery slice unchanged.
- Existing installs migrate to persist v5 with habits and history intact.
- `jest` green including new selector, action, and migration tests; `tsc` and
  eslint clean; the app builds and the tab works on the simulator in both
  light and dark mode.

Existing pipeline covers this — personal iOS build installed from Xcode; no new
channel, no store submission.

## What I noticed about how you think

- You described the output before the input: "for the month of septemeber i went
  grocery shopping for 6 times, in that i went to 4 times to lidl and 2 times to
  esselunga, overall spent 200 euros". Starting from the sentence you want the
  app to be able to say is why the trip-first data model was obvious within a
  minute instead of after a rewrite.
- You caught a modelling decision before it was asked: "to create this maintain
  it separately, so while inputting the things i can select it" — that is the
  store registry earning its own lifecycle, and you spotted it while listing
  features.
- You bounded the feature yourself with "all these has to stay inside the
  grocery tab", which is the kind of line that keeps a side feature from
  leaking into three other screens.
